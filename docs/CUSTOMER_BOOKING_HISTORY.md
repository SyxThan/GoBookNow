# Customer booking history and safe recovery

## Source of truth and API

`GET /api/v1/bookings/me` lists bookings from PostgreSQL by the authenticated
`CUSTOMER` user's `Booking.customerId`. It accepts `status`, `from`, `to`,
`search`, `page` and `limit` (maximum 100). Results use `createdAt DESC, id DESC`
and include pending holds even before a Payment exists. `GET
/api/v1/bookings/:bookingId` returns the same owned projection for a stable
detail URL. Both endpoints are read-only. Cross-owner detail IDs return 404.
Money is serialized as decimal strings. The projection contains booking item
snapshots, the latest payment attempt's status and safe merchant reference,
refunds and a count of active tickets. It excludes signed checkout fields,
provider secrets, QR tokens and internal banking payloads.
Date-only `from`/`to` filters cover the full calendar day in Vietnam time;
timestamp inputs retain their supplied offset.

## Display states

The database retains its existing Booking, Payment, Refund and Ticket enums.
The customer read service derives these view-only states:

| Booking and related facts | Customer display |
| --- | --- |
| Unexpired pending hold, no Payment | `WAITING_PAYMENT` |
| Unexpired pending hold, Payment exists | `WAITING_CONFIRMATION` |
| Confirmed booking | `CONFIRMED` |
| Expired hold or expired Booking | `EXPIRED` |
| Cancelled booking | `CANCELLED` |
| Any pending refund | `REFUND_PENDING` |
| Completed refund, none pending | `REFUND_COMPLETED` |

The UI also shows the raw facts as translated labels. A successful Payment on
an expired Booking never means a confirmed reservation. Tickets are fetched
through the existing owned ticket/QR APIs only when available.

## Payment recovery

Opening history or detail performs GET requests only. An explicit payment
button calls the existing initiation endpoint only for an unexpired, positive
value hold with no Payment. The backend rechecks ownership, hold time and
financial state under the existing booking row lock. It uses one Payment per
Booking and reuses a live pending PaymentAttempt and merchant reference. The
SePay checkout form is generated by that endpoint and is never stored in the
history response.

Once a Payment exists, the customer sees its status and can refresh. The
customer UI does not offer another payment action because an absent IPN does
not establish that no transfer happened. The existing valid SePay IPN path
alone confirms a Booking and issues tickets. A late successful IPN leaves the
Booking expired and creates a pending system-correction refund obligation.
Expired bookings link to a fresh service selection; viewing them never creates
a new hold.

## Fresh sessions and refresh

`/bookings` and `/bookings/[bookingId]` query the backend using the current
session token. Query keys include that token; the shared auth provider clears
private query data on account/session change. No device-local recent-reference
list is used as a history source. The detail countdown reads the persisted
`expiresAt` and compensates for the response's `serverTime`. Expiration causes
one authoritative refetch. Pending detail polls every five seconds while
visible, for at most 15 minutes from mount; mount, focus, reconnect and the
manual button can also refresh it. Terminal states stop the interval.

## Verification

`customer-booking-history.int-spec.ts` uses isolated real PostgreSQL to check
ownership, pagination, snapshots, pending/confirmed/expired/cancelled/refund
projections and authenticated IPN. `booking-history.test.tsx` checks that the
list does not require device references and that payment is an explicit
action. `customer-booking-journey.e2e.spec.ts` covers leaving checkout,
reloading, a new browser context, pending state and valid synthetic IPN on
desktop and mobile. The existing payment edge-case suite protects late success,
idempotency and financial concurrency. CI runs the integration and three-portal
browser suites against isolated test databases.
